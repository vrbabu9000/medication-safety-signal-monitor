From FDA files to a signal, one stage at a time

This page follows real data through every step we will build: download, drug identity, dedup, counting, the ontology, then Part B (the AI reading the label). Every number below was measured on the two latest FAERS quarterly files (2026 Q1 + Q2, 819,683 reports) by prototypes/explore/faers_bulk_walkthrough.py. Nothing is illustrative unless it says so.

Running example: semaglutide (Ozempic, Wegovy, Rybelsus) and the eye condition NAION (sudden vision loss from poor blood flow to the optic nerve). Second example: oxycodone.

Overview

The shape of the whole thing

Part A turns raw FAERS reports into one number per drug and reaction: "how many reports, and how unusual is that?" Part B turns a label document into a list: "which reactions does the label already mention?" The app shows the reactions that are frequent and unusual in Part A but missing from Part B's list.

The funnel below is what happens to FAERS rows on their way through Part A. Each stage throws away or corrects something, and every one of those choices is a design decision.

Get the data

What it is

FDA publishes FAERS as one zip per quarter (about 63 MB). Each zip holds 7 linked tables and a delete list. This is what the pipeline ingests (decision D004). The openFDA API we explored earlier is a different, pre-processed copy and stopped updating on 2026-07-30. The bulk files still arrived for Q1 and Q2 2026.

What's messy (measured)
  • Files are $-separated with Windows line endings and Latin-1 text. A standard CSV read breaks.
  • The delete file has no header and starts with a blank line.
  • No openfda block in bulk files. No RxCUI and no label setid. Our earlier docs said "FAERS links straight to the label". That is only true in the API copy.
  • The useful bridge is nda_num, the FDA application number. It is filled on 79% of semaglutide rows and separates products cleanly: 209637 = Ozempic injection (10,800 rows), 215256 = Wegovy (5,580), 213051 = Rybelsus (532). route is blank on 89% of them.
Decision to propose
  • Land each quarter's zip untouched in a raw dataset, one partition per quarter. Parse with an explicit schema (delimiter, encoding, all columns as text).
  • Link FAERS rows to labels through nda_num → application number on the label. Do not rely on openFDA enrichment.
2

Drug identity: which rows are "our" drugs?

What it is

Every drug row has two name fields: drugname (what the reporter typed) and prod_ai (the active ingredient FDA coded). We must turn both into one of our 13 ingredients. This happens once, in one place, for all sources. The brief grades exactly that.

What it actually looks like

Distinct spellings of one ingredient in a single quarter: oxycodone 77, tramadol 66, hydrocodone 63, morphine 53. A sample for oxycodone:

OXYCODONE                                   2,861 rows
OXYCODONE HYDROCHLORIDE                     2,001
ACETAMINOPHEN\OXYCODONE HYDROCHLORIDE         572   ← combination product, "\" separates ingredients
OXYCONTIN                                     518   ← brand
OXYCODONE TEREPHTHALATE                       478   ← different salt
PERCOCET                                      380
NALOXONE HYDROCHLORIDE\OXYCODONE HYDROCHLORIDE 125
What's messy (measured)
  • A simple "contains the word" match is wrong. "morphine" also matches apomorphine, a Parkinson's drug (ONAPGO 1,021 rows, APOKYN 478), and heroin (coded DIAMORPHINE, 117). Morphine rows in Q2: 5,058 by substring vs 3,362 by exact ingredient. That is 50% false hits.
  • "fentanyl" also matches parafluorofentanyl, an illicit street analogue. "methadone" also matches levomethadone.
  • Compounded mixes appear: CYANOCOBALAMIN\SEMAGLUTIDE, PYRIDOXINE\TIRZEPATIDE. These are pharmacy-made, not FDA-approved products.
  • prod_ai is blank on 342 of our rows per quarter. Those need the brand or drugname as a fallback.
Decision to propose
  • Split prod_ai on \, strip salt words, then match the exact ingredient through RxNorm. Never use substring matching.
  • A combination product counts for each of our ingredients in it and carries a combo tag. Compounded mixes carry a compounded tag.
  • Output: one drug_identity table (raw string → ingredient RxCUI, plus how it was matched). Recalls and labels reuse the same table.
3

Drug role: was our drug blamed?

What it is

Each drug row has a role: PS primary suspect, SS secondary suspect, C concomitant (just also being taken), I interacting. A report lists everything the patient took, so most drugs on it are bystanders.

What it actually looks like
case 26453439 (Q1)
DRUG seq 1  PS  OZEMPIC  SEMAGLUTIDE
DRUG seq 2  SS  OZEMPIC  SEMAGLUTIDE     ← the same drug listed twice
case 26496412 (Q1)
DRUG seq 1  PS  OZEMPIC  2 mg /WK
DRUG seq 1  PS  OZEMPIC  0.25 mg /WK     ← dose titration = two rows, same drug_seq
What's messy (measured)
  • In Q1, 31,381 of 45,160 SS rows for our drugs (69%) are the same ingredient that is already PS in the same report. SS often just means "the same drug again".
  • Our ingredient appears more than once in the same report 14,063 times in Q1. Counting rows instead of reports would double-count.
  • Tirzepatide has more SS rows (28,389) than PS rows (19,703) in Q1. "PS only" would throw away real reports.
Decision to propose
  • Suspect = PS, SS or I. Count each ingredient once per report. Concomitant is kept in the data but never counted toward a signal.

Case versions and deletes: the incremental step

What it is

A case gets follow-up reports. Each follow-up is a new caseversion and gets a new primaryid. A follow-up can arrive in a later quarter. The newest version replaces the old one completely; it is not added on top. FDA also withdraws cases through the delete list.

What it actually looks like: case 26412122, Q1 → Q2

In Q2, Victoza, Trulicity and Mounjaro are gone. If we simply append Q2 to Q1, liraglutide, dulaglutide and tirzepatide each keep a phantom report that the reporter has since corrected.

What's messy (measured)
  • Append vs replace: appending each quarter gives 422,872 drug-reaction rows for our drugs. Replacing by case gives 389,074. That is 33,798 phantom rows (+8.7%) after only two quarters, and it grows every quarter.
  • Of 4,217 delete IDs in Q2, only 655 point at Q1. The rest point at older quarters. Deletes reach back into all of history.
  • One case is on version 46.
Decision to propose
  • Incremental = upsert by caseid: keep the highest caseversion, then apply every delete file against the full case table.
  • Raw quarters are append-only (cheap, incremental). The faers_case_latest table is a snapshot that updates only the changed cases. Counts are recomputed on top (small).
  • Optimization log entry: "append vs upsert" with these before/after numbers.
5

Hidden duplicates: one patient, hundreds of case IDs

What it is

Dedup by caseid assumes one patient has one case. That breaks when many companies each file the same patient, often from a published paper. FDA gives each filing its own caseid.

What it actually looks like

Before this step, oxycodone's "top signals" were these:

ReactionReportsPRRPlausible for an opioid?
Duodenal ulcer perforation514306no
Pemphigus (blistering skin disease)589240no
Hand deformity526225no
Glossodynia (burning tongue)590154no

Each one traces to a 43-year-old woman in Canada, filed by Sandoz, Novartis, Amgen, Teva, Haleon, Celltrion and others. There are 332 case IDs in Q1 and 370 in Q2. Each filing lists 40–150 drugs and 24–59 reactions, with no event date.

What's messy (measured)
  • Rule tested: same age + sex + country + event date, 30 or more drugs, 50 or more filings = one patient. It found 7 such patients, all in Canada, and folded 1,530 reports into one each.
  • Effect on suspect reports: oxycodone 4,464 → 3,408 (−24%) · tramadol 3,032 → 2,470 (−19%) · hydromorphone 1,298 → 1,023 (−21%) · buprenorphine −13% · morphine −10% · all GLP-1s 0%.
  • After the fold, oxycodone's top list makes sense: drug dependence (506), drug diversion (467), pain, overdose. Some residue remains: rheumatoid arthritis (219) and joint swelling (233), from the same woman recorded as age 44. The rule catches most of it, not all.
Decision to propose
  • Add a cross-case duplicate step after the version dedup. Keep the simple rule for the pilot. Show the residue honestly; fuzzy matching goes on the roadmap.
  • Monitoring: alert when one "person key" exceeds 50 filings in a quarter.

A field changed meaning between quarters

What it is

occp_cod says who reported: MD doctor, PH pharmacist, HP other health professional, CN consumer, LW lawyer. We planned to tag lawyer-filed reports with it (D016).

What's messy
  • Consumer reports did not drop by 90% in real life. The field stopped being filled, most likely because of FDA's March 2026 switch to its new AEMS system. Any rule built on this field quietly breaks from Q2 on. This is exactly the drift the boss wants monitoring to catch.
Decision to propose

  • The lawyer tag uses occp_cod where it is filled and is shown as "unknown" where it is not. We do not guess.
7

Explode, tag, count, score

What it is

Each clean case becomes one row per (our suspect ingredient × reaction). Each reaction gets a bucket tag. Then we count reports per ingredient and reaction, and compute the PRR.

PRR (proportional reporting ratio): among semaglutide reports, what share mention NAION, divided by that share among all other reports. 1 means normal. The standard screen (Evans) flags PRR ≥ 2 with at least 3 reports and χ² ≥ 4.

What it actually looks like: case 26412122 after Q2
caseid    ingredient   reaction                    bucket
26412122  semaglutide  Impaired gastric emptying   clinical
26412122  semaglutide  Off label use               product_use_error

The PRR is built from a 2×2 table, here for semaglutide + NAION, 2026 H1:

                          NAION     no NAION
semaglutide suspect         394       20,640     (21,034 reports)
all other reports           129      769,653     (769,782 reports, after the stage 5 fold)
PRR = (394 / 21,034) / (129 / 769,782) = 112

What's messy (measured)
  • A high PRR is not always a safety issue. "Weight loss poor" (PRR 129) means the drug did not work. "Device leakage" is a pen problem. Without bucket tags, these would top the list.
  • One eye problem is spread over about 10 different MedDRA terms. Counting them one at a time understates it. We cannot use MedDRA's own grouping without a licence, so we need our own small term groups for the pilot.
  • Headache has 594 reports but PRR 0.9. It is common with every drug. Raw counts alone would rank it high.
Decision to propose
  • Rank on PRR + Evans criteria (D006), only within the clinical bucket. Other buckets are visible but not ranked (D016).
  • Keep a small hand-made term-group list (e.g. "optic nerve disorders"). Write the licensing reason down.
  • Counts per quarter, so "what changed since last time" is a simple difference.

What becomes the ontology

What it is

Datasets are tables. The ontology turns the rows the safety officer clicks on into objects with links between them. Rule of thumb: if she needs to click it, open it, or change it, it is an object. If it only feeds a number, it stays a dataset.

9

Part B: the AI reads the label

What it is

Part A tells us what people report. Part B tells us what the label already says. Labels are long XML documents with prose, bullets and tables. The LLM reads the safety sections and returns one row per reaction, with the exact quote it came from.

Step 9a · pick the right label

DailyMed has 7 labels named "Ozempic". Two matter:

27f15fac…  v14  2026-08-19  OZEMPIC (ORAL SEMAGLUTIDE) TABLET / RYBELSUS TABLET
adec4fd2…  v20  2026-06-10  OZEMPIC (SEMAGLUTIDE) INJECTION        ← the one most FAERS reports are about
(+5 repackager copies from A-S Medication Solutions)

The tablet label says nothing about injection sites. The injection label mentions them 20 times. Compare against the wrong label and "injection site pain" turns into a false signal (DQ33). The bridge is FAERS nda_num 209637 → the injection label.

Step 9b · cut out the safety sections

Sections carry LOINC codes. The raw XML of the Adverse Reactions section:

<section><code code="34084-4" displayName="ADVERSE REACTIONS SECTION"/>   ← found by code
  <section><code code="42229-5" displayName="SPL UNCLASSIFIED SECTION"/>
    <title>6.2 Postmarketing Experience</title>                              ← generic code!
    <item><content>Gastrointestinal</content>: acute pancreatitis and necrotizing
          pancreatitis…; ileus, intestinal obstruction…</item>

Subsections 6.1 and 6.2 use the generic code 42229-5, so searching by code alone misses them. We take everything nested under the four parent codes: Boxed Warning, Contraindications, Warnings & Precautions, Adverse Reactions. Tables come out as rows:

Diarrhea         | 4                 | 9              | 10

Why a plain word search fails (real text from this label)
Words in the labelWord search saysTruth
"blurred vision"on labelListed as a symptom of low blood sugar, not a side effect of the drug
"gastroparesis"on label"not recommended in patients with severe gastroparesis": an existing condition
"delays gastric emptying"on labelHow the drug works (said in §5.10 and §7), not a listed adverse reaction. FAERS "Impaired gastric emptying" has 1,883 reports, PRR 69. Needs a rule.

Decision to propose
  • The LLM returns each reaction with its section, its context (adverse reaction / symptom of something else / pre-existing condition / mechanism) and a quote. Only "adverse reaction" counts as labeled.
  • Grounding check: code confirms that each quote exists word for word in the label. A quote that doesn't exist is a hallucination and is counted.
  • Gold set: you hand-list reactions for about 10 labels. LLM vs you gives precision, recall and F1 (target 0.85, D015).
  • Incremental: DailyMed publishes daily and weekly update zips. Re-run the LLM only for a new (setid, version). Cache by (setid, version, section, prompt version, model). Note: this label's history lists version 13 twice (May 18 and May 20), so the version number alone is not a safe key; include the publish date.

Your question

You're right, with two limits

You're right: B, C and D all depend on how well we understand the data. This pass proves it. The first real look at the bulk files overturned three things we had written down: the FAERS→label link, the "suspect only" rule, and the reporter-type tagging. That would have surfaced mid-build otherwise.

Limit 1, depth where the signal lives. FAERS, labels and drug identity are the spine of every flag. They deserve this depth. Recalls need a half-day pass (NDC parsing, "ongoing" meaning). ClinicalTrials.gov is optional; it can stay light. Equal depth everywhere would eat Week 1.

Limit 2, depth must become the build. The script behind this page already is the FAERS pipeline in plain Python: same stages, same rules. Moving it into Foundry transforms is translation, not new design. Timebox the remaining understanding to the label (Part B) walk and recalls, then build.
